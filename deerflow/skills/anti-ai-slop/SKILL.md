# Anti-AI-Slop

AI-generated UIs share a recognizable "look" because models sample the median of
their training data. Absent direction, they reach for the same handful of
patterns — indigo/purple gradients, Inter, evenly-sized cards, plastic stock
imagery, hedgy copy. The result is technically fine and instantly forgettable.

This skill exists to break that default. It works in two moves: **anchor to real
human design first**, then **build and critique against a concrete checklist** of
what makes design read as bespoke. Do both — references without rules drift back
to defaults; rules without references produce sterile "correct" pages with no
point of view.

## Workflow (do these in order)

### 1. Anchor to real references FIRST — before writing any UI

Do this before choosing colors, fonts, or layout. Real references are the single
strongest antidote to slop.

- **Use the Refero MCP if it's connected.** Refero (refero.design) is a curated
  library of high-quality real product screens. Search it for the specific
  surface you're building — by product category and by flow, not generic terms.
  Search things like "fintech onboarding," "settings page," "pricing page SaaS,"
  "empty state dashboard," "multi-step form." Pull 2–4 screens and extract *what
  makes them work*: type scale, spacing rhythm, color restraint, how they handle
  hierarchy and empty/edge states. See `references/refero-mcp.md` for how to call
  it and how to set it up if it isn't connected yet.
- **If Refero isn't available,** name 2–3 specific real products whose design
  fits the brief (e.g. Linear, Stripe, Vercel, Things, Notion) and reason from
  what they actually do — don't invent a generic "modern SaaS" look.
- Translate references into concrete constraints for *this* build: a named type
  pairing, a specific palette, a spacing scale, a motion approach. Write these
  down before coding so defaults can't creep back in.

### 2. Build with the anti-slop rules applied

Read `references/ai-slop-checklist.md` and hold to it while building. The short
version, in priority order:

1. **Kill the giveaway defaults.** No indigo/purple→blue or purple→cyan
   gradients as the primary look. Not Inter/Roboto/Arial as the display face
   without a deliberate reason. No glassmorphism-with-neon-glow.
2. **Give type a point of view.** Pick a real type pairing with a distinctive
   display face and a readable body face; set a deliberate scale. Typography is
   the fastest way a design reads as human.
3. **Vary rhythm and hierarchy.** Break out of uniform 16px/24px radii and
   identical card sizes. Real layouts have a focal point and intentional
   asymmetry — not N identical boxes in a row.
4. **Use real content and imagery.** Real screenshots, real copy, real numbers
   over stock "diverse team at laptops" photos and smooth AI illustrations. If
   placeholders are unavoidable, make them specific and plausible.
5. **Write copy in a human voice.** Specific over aspirational. Cut "Build the
   future / all-in-one platform / cutting-edge / best-in-class" and hedges like
   "may help." Say the concrete thing the product does.
6. **Design the boring states.** Empty, loading, error, hover, focus, disabled.
   Their absence is a dead AI tell — and their presence is what real products
   ship.
7. **Motion with intent.** Micro-interactions that signal state or guide
   attention; no uniform fade-ins or reflexive hover-bounce.
8. **Accessibility is part of not-looking-cheap.** Real focus rings, WCAG-passing
   contrast, semantic markup, keyboard paths. AI output routinely skips these.

Per-stack specifics (Tailwind config, plain CSS, no-code exports) are in
`references/stack-notes.md`.

### 3. Critique and fix in a loop — don't ship the first pass

A one-shot build can't escape slop; a loop can. After building, review the output
against `references/acceptance-bar.md` (a ~12-item pass/fail bar). For each item
that fails, fix the highest-impact one, then re-check. Repeat until it passes or
you stop making meaningful gains. When reviewing existing UI ("audit mode"), run
this same bar and report failures with specific fixes.

## The two failure modes to avoid

- **Reverting to defaults** because it's easy — the whole point is not to. If you
  catch yourself reaching for indigo + Inter + three cards, stop and pull a
  reference instead.
- **Over-correcting into "weird for weird's sake"** — brutalism, clashing type,
  and chaos are just a different slop. Distinctive still has to be usable,
  accessible, and appropriate to the product. Restraint reads as expensive.
